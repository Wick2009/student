Building a Domain-Scoped AI and a CSS-Powered Accessibility System

Inside the Groq API backend and the CSS custom property architecture that powers the toolkit.

May 26, 2026 · 7 min read
Posts Personal Experience Project Highlights Technical Deep Dive

Two technical systems define most of my work on this project. The first is the Groq backend that powers the UESL Coach chatbot and page summarizer. The second is the CSS architecture that makes the toolkit work across every component of the site without touching any of them individually. Both involve decisions that are easy to get wrong in ways that do not surface until something breaks at scale.

Starting with the backend. I built six API endpoints in groq_api.py on a Flask Blueprint with the /api prefix. The simpler ones are /api/groq (a basic chat passthrough), /api/groq/chat (an enhanced version that returns usage metadata), /api/groq/models (a list of available models with descriptions), and /api/groq/health (a health check). The more interesting ones are /api/groq/analyze and /api/uesl-chat.

The /api/groq/analyze endpoint handles text analysis tasks. When the task is summarization, it runs with temperature 0.3 and a system prompt focused on factual accuracy: "You are a text analysis expert. Respond clearly and concisely." Temperature 0.3 keeps the model close to the most probable output — less creativity, more reliability. That is the right setting for a tool that needs to distill content accurately rather than riff on it.

The /api/uesl-chat endpoint is built differently. It uses temperature 0.7 for warmer, more varied responses, and it has a hardcoded system prompt that is not configurable at runtime. The prompt gives the model a specific identity: UESL Coach, a friendly assistant that only answers questions about the Unified Esports League. The knowledge baked into the prompt covers the program's mission, the 1:3 coach-to-client ratio, the age range (8 and up), the cost structure (free for San Diego Regional Center clients), the seven tech center locations, and Spanish-language contact information. The prompt ends with a hard behavioral instruction: keep answers to two to four sentences and stay encouraging.

Hardcoding the system prompt was a deliberate choice. The UESL Coach is not meant to be a general chatbot — it is meant to be a predictable, trustworthy assistant for an audience that benefits from consistency. Making the prompt configurable at runtime would open the door to the model drifting outside its intended scope, which is exactly the failure mode this design is trying to prevent.

Context management in the chatbot uses a sliding window. Each POST request to /api/uesl-chat sends the last ten messages from the conversation history along with the system prompt. On the frontend, the Summarize Page input is truncated at 1800 characters before being sent. These two constraints together keep the token budget predictable across long sessions without breaking conversational coherence.

The CSS architecture works on a similar principle of constraining scope to get broad effects. The high-contrast and dyslexia font toggles in the toolkit do not write any per-component CSS. Instead, they add a class to the html element — tk-high-contrast or tk-dyslexia — and the corresponding CSS redefines a set of custom properties at the root level.

High contrast remaps eight variables at once: --bg becomes #000, --surface becomes #0d0d0d, --text becomes #fff, --cyan becomes #ff0, and the remaining surface and border variables follow. Because every component in the UESL site uses these design tokens rather than hardcoded color values, the entire site switches to high-contrast without a single per-component rule. If the site has fifty components, you do not write fifty overrides. You write eight variable definitions and the CSS cascade handles the rest automatically.

The dyslexia font works the same way. The @font-face declaration for OpenDyslexic is injected into the document only when the toggle is first enabled, not on page load, which avoids an unnecessary CDN request for users who never use the feature. The CSS then applies to every text element: font-family, letter-spacing at 0.04em, word-spacing at 0.1em, line-height at 1.7. Comic Sans is the declared fallback if the CDN fails — not a visual ideal, but it preserves the wider spacing properties that matter most for readability.

Both systems share the same underlying principle: define the constraint at the right level of abstraction, and let everything below it respond automatically. For the AI, that level is the system prompt. For the CSS, it is the root custom properties. Getting that layer right means the system scales without accumulating technical debt every time something new is added to the site.
